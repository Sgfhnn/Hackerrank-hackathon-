# FINDINGS: how the 32 solved samples are built

Reverse-engineered from `dataset/sample_deletion_requests.csv` + `sample_output.csv` by Hark (evidence
ingestion + state engine). Every rule below is implemented in `code/hark/` and reproduces **30/32 sample cases
exactly** (status acc 1.00, step P 1.00 / R 0.99 / F1 0.995, evidence-id acc 1.00). The per-step trace
for every sample (how the resource was linked, which file/activity proves its state) is in
`sample_explanations.md` (generated by `code/hark/explain_samples.py`).

## 0. Data gotchas
* **All timestamps in the files are ISO-8601 UTC** (`2026-01-04T14:56:29Z`), with seconds. Some tool
  output (and this team's chat tooling) shows them localized as `Sun 2026-01-04 5:56 PM EAT`. Parse ISO;
  compare in UTC. The seconds matter (see section 3).
* Evidence manifest `captured_at` is the export time of the file. A file can contain rows/log lines
  stamped *before* `audit_at` while the file itself is captured *after* it (e.g. `evidence_06`,
  `evidence_12`, `evidence_02`). Those files are **not citable** and must not drive the state
  (sample case_27: `evidence_02` shows account_3866 present at 09-17 > audit; gold says ABSENT with `evidence_92`).
* Every request email resolves to exactly one user_id (current email or historical email in
  `user_audit_log.csv`). Gather all identifiers: emails, phones (digits only), names, email hashes,
  including old values from the audit log (case_12 finds analytics_9914 by the **old email hash**;
  case_10 finds support_002 by the **old email**; case_29/30 use old emails).
* Decoy identifiers exist (`smartinez6461.jr@gmail.com` vs `smartinez6461@gmail.com`, `Jonas Berglund`
  vs `Jonas Berg`): match emails/phones/hashes/user_id exactly; do not match on names alone.

## 1. Which resources belong in a case
The gold step list of an authorized deletion = **every resource of the subject** (account, retained
security audit record, and every downstream copy), not just the broken ones.
1. **Evidence links**: any observation (SQL row, JSON record, handover line, log line) carrying one of the
   subject's identifiers. Logs: the identifier is usually on the `*_started` line (`lookup_key`,
   `match_key`, `subject_key`, `scan_key`, `subject_ref`) and the `resource_id` on the `*_completed` line of
   the same `trace_id`; join by trace. `subject_reference=user_NN` links security audit records,
   tombstones, legal holds, connectors, backups.
2. **Deletion-worker activity cluster** (for records with no identifier left, e.g. anonymized analytics or
   accounts whose lookup returns only a 404 with no key). Every case has **exactly one** account activity
   (`DELETE_RECORD ... submitted primary profile` or `CLASSIFY_REQUEST` for non-deletion). Relative to the
   case's `reported_at` R:
   | activity details phrase | offset from R |
   |---|---|
   | `Deletion worker submitted primary profile X` (account) | R-75 .. R-45 min |
   | `Policy action completed for X` (successful ANONYMIZE/REDACT/DISABLE/BLOCK/RETAIN) | R-28, R-21, R-14, R-7 min |
   | `received the final result for X` / `Connector status check` / `Restore-access check` | R+38 .. R+115 min |
   | hand-made cases 01-10: `reported the requested operation` / `stopped after` | R-6 .. R+9 min |
3. **Second-level fingerprint** (resolves cases that share the same reported_at; ~2.2 cases per R):
   with d = seconds between the case's account activity and a follow-up activity,
   `Policy action completed` has d mod 30 in {9,10,11} (d in 900..4500 s) and
   failure/check chain events have d mod 30 in {20,21,22} (d in 4500..11500 s).
   A case's policy events and failure chain never mix (a case is either a "worker succeeded" or a
   "worker failed" case). Algorithm in `code/hark/engine.py: Engine.prepare()`: owner evidence -> account per case by
   fingerprint with evidence-owned follow-ups -> claim un-owned follow-ups -> elimination -> last-resort
   deterministic guess (38 test cases had no signal left).
4. **Multimodal artifacts**: each PNG/PDF has exactly one `LINK_RESOURCE_IDENTITY` activity (activity time =
   file captured_at + 7 min) naming resource, email and user_id. It belongs to the case whose
   `[requested_at, audit_at]` contains that LINK, NOT to every case of that user (sample case_07 ignores
   object_19 of Feb; case_17 ignores tombstone_17 of March). These are 12 test cases: 33,34,35,39,45,46,50,52,
   53,55,61,63 (users 18,11,13,14,03,17,20,18,22,16,07,09). States are in `code/hark/multimodal_hints.py`
   (provisional, read by hand from OCR; replace with the teammate's extractor).
5. Hand-made family (users <= ~22, cases 01-10 and the multimodal test cases): account id is
   `account_0NN` for `user_NN` (10/10 samples, incl. case_04 where no activity mentions it).
6. Not visible anywhere: case_18 `audit_record_6645`, case_20 `audit_record_5569` (grep finds them in no
   file, image or activity) -> unrecoverable; accept the miss.

## 2. Category -> rule -> operations
Treatment follows the resource prefix, refined by **the deletion worker's own event_type**:
| resource | rule | present & non-compliant | already compliant |
|---|---|---|---|
| account_* (USER_PROFILE) | DELETE | REPORT_REMAINING_RECORD, DELETE_RECORD, VERIFY_RECORD_ABSENT | VERIFY_RECORD_ABSENT (always included) |
| search_*, export_*, marketing_*, object_* | DELETE | same as above | VERIFY_RECORD_ABSENT |
| support_* message (support_conversations, tickets, `message_pii_scan`, handover SUPPORT_MESSAGE, worker REDACT_RECORD) | REDACT | REPORT_EXPOSED_PII, REDACT_RECORD, VERIFY_RECORD_REDACTED | VERIFY_RECORD_REDACTED |
| support_* attachment (ticket_attachments, `attachment_pii_scan`, handover SUPPORT_ATTACHMENT, `support_replica` contact rows, worker DELETE_RECORD) | DELETE | REPORT_REMAINING_RECORD ... | VERIFY_RECORD_ABSENT |
| analytics_* | ANONYMIZE, **but DELETE when the worker issued DELETE_RECORD** or it is a `contact_lookup` (email_opt_in) record found by hash (case_12) | REPORT_EXPOSED_PII, ANONYMIZE_RECORD, VERIFY_RECORD_ANONYMIZED | VERIFY_RECORD_ANONYMIZED |
| tombstone_* (ACCOUNT_TOMBSTONE) | REDACT (keep subject_reference user_id) | REPORT_EXPOSED_PII if name/email/phone/hash set (case_32) | VERIFY_RECORD_REDACTED (case_31) |
| audit_record_* (SECURITY_AUDIT_LOG), legal_hold_* | RETAIN | (delete only if retention_until < audit_at; never seen) | VERIFY_RECORD_PRESENT |
| data_flow_* | disable | enabled=true / ACTIVE -> REPORT_ACTIVE_DATA_FLOW, DISABLE_DATA_FLOW, VERIFY_DATA_FLOW_DISABLED | enabled=false -> VERIFY_DATA_FLOW_DISABLED |
| backup_* (BACKUP_ARCHIVE) | RETAIN + block | restore_allowed=true / eligible=true / ACTIVE -> REPORT_RESTORE_RISK, BLOCK_RESTORE, VERIFY_RESTORE_BLOCKED | restore_allowed=false / decision=deny -> VERIFY_RESTORE_BLOCKED |
PII = any of name/email/phone/email_hash non-null (a bare user_id reference is allowed). A search entry is
REMAINING regardless of PII.

## 3. State at audit_at
* Latest **citable** file (manifest captured_at <= audit_at) that observes the resource wins; activity
  `reported_result` is only a claim (case_02 PARTIAL delete + evidence_54 absent => COMPLETE; case_11
  FAILED and still FOUND; case_24 SUCCESS delete but replica re-synced it => REMAINING; case_16 search
  delete SUCCESS but read-replica still has it).
* Inside one SQL snapshot, a row in *any* table (primary, read/regional/reporting/failover replica) means
  the copy exists (case_05 account only on failover replica; case_16 account only on read replica).
* Inside a log, only the latest reading of that resource counts (lookup 200 on 09-10, 404 on 09-16 => absent).
* **No citable evidence about a resource => no finding** (a finding must cite evidence); emit only its
  verification step (cases 18/20/22/23/29/30/31/32 accounts with FAILED/PARTIAL deletes are
  VERIFY_RECORD_ABSENT only).

## 4. Evidence ids
* FINDING: the latest citable file showing the violation (all samples cite a file_id, never an activity).
* COMPLETE: each VERIFICATION cites the latest citable file showing the compliant state of that resource
  (case_21/25-28 all `evidence_92`; case_03 `evidence_94`; case_04 account from `evidence_54`, analytics
  from `evidence_56`).
* Account absent with no direct lookup: cite the latest citable **account-service snapshot** that does not
  contain it (SQL with customer_profiles* tables or bundle with an account_service collection, even an
  empty one): case_01/02/04 -> `evidence_54`, case_31 -> `evidence_51`. A direct lookup (404) beats a
  generic snapshot (case_21: `evidence_92` not the later `evidence_51`).
* INCOMPLETE: remediation and all verification steps have `evidence_id=""`.

## 5. Status and ordering
* INCOMPLETE iff at least one finding; otherwise COMPLETE (verification only).
* Order = phase, then the operation order of the problem-statement table, then system_id, then
  resource_id (string ascending). Verification lists every resource of the case (compliant ones too).

## 6. NOT_APPLICABLE cues
Exactly 10 test texts are non-deletion and there are exactly 10 `CLASSIFY_REQUEST` activities
("classified request for account_X as non-deletion"). Cues: "not asking for deletion", "keep the account",
"leave my profile", "don't delete", "do not close", "without removing", "marketing lists only",
"continue using", "download my ... portable", "a copy of", "replace it with the new one", "correct it",
"change the email", "resetting the login", "information request / what personal information you hold".
All 32 samples are deletions (incl. French, Spanish, Japanese texts).

## 7. Open problems
* 38 test cases share a reported_at slot with another case and have no fingerprint signal (only account
  + audit record): account chosen by a deterministic guess (~50%).
* Multimodal states are hand-read (multimodal_hints.py); legal_retention_register PDF (users 08,12,17,21,24,29)
  has no matching resource ids and is unused.
* Linking uses record-level time <= audit_at (needed for case_23 audit_record_4128 which only appears in a
  file exported after audit), and ownership exclusion uses all evidence regardless of time.
* RESTORE_BACKUP activity_3387 (backup_9287 repopulated search_4882 on 08-22) is not modelled beyond the
  backup hint.
